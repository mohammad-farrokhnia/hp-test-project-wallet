# State machines

Deposits and withdrawals change status only through these tables. Each row is one allowed transition. Anything else is rejected by the module's `StateMachine.next()` and by a compare-and-set update (`… WHERE status = $expected`). Every applied transition also writes a `state_transitions` row. The API exposes these statuses directly; `SUCCEEDED` and `FAILED` are final.

**Two rules hold everywhere** (ADR-3):
- A callback or webhook never moves a status. It only schedules a sync, and the sync's own lookup (`GET` or `verify`) decides.
- Silence, timeouts and 503s never move a status to `FAILED`. They reschedule, and after 30 minutes they flag the record for review while the money stays frozen.

## Withdrawal

Normal path:

```
PENDING  ->  SUBMITTING  ->  PROCESSING  ->  SUCCEEDED
```

| Status     | Meaning                                                                                                                              | Can move to                                  |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| PENDING    | Accepted, money frozen, waiting for a worker                                                                                         | SUBMITTING (W1), FAILED (W13 cancel)         |
| SUBMITTING | Sending to the provider. On 503 or timeout it stays here and checks later (W3). On GET 404 it resubmits with the same requestId (W5) | PROCESSING (W2), SUCCEEDED (W8), FAILED (W6) |
| PROCESSING | Provider accepted, waiting for the result                                                                                            | SUCCEEDED (W8), FAILED (W9)                  |
| SUCCEEDED  | Final. If the bank later returns the money, a return journal is written but the status stays (W10)                                   | none                                         |
| FAILED     | Final. Only exception: the bank paid it after all (W12, an audited correction, Ambiguity #1)                                         | SUCCEEDED (W12 only)                         |

| W11 | SUBMITTING, PROCESSING                           | Sync: GET RETURNED (first final status we see)                                           | —                                              | SUCCEEDED  | `WITHDRAWAL_SETTLE` then `WITHDRAWAL_RETURN`, one transaction                            | as W8 + W10                                                                                      | none                                  |
| W12 | FAILED                                           | Sync: GET SUCCEEDED or RETURNED (a signed webhook for the final withdrawal triggered it) | —                                              | SUCCEEDED  | `WITHDRAWAL_LATE_SUCCESS` (PAYOUT_CLEARING +x, AVAILABLE −min(available, x), DEBT −rest) | `late_success_at`; `needs_review = LATE_SUCCESS`; alert. Daily usage is not re-reserved (ADR-10) | none                                  |
| W13 | PENDING                                          | Cancel (API, bonus)                                                                      | still PENDING under the row lock               | FAILED     | `WITHDRAWAL_RELEASE`                                                                     | `failure_reason = CANCELLED`; usage released. From SUBMITTING onwards → 409 `CANCEL_NOT_ALLOWED` | none                                  |
| W14 | any non-final                                    | Stuck (sweeper)                                                                          | older than 30 min, not yet flagged             | unchanged  | —                                                                                        | `needs_review = STUCK`; alert; money stays frozen                                                | every 5 min, indefinitely             |
| W15 | SUCCEEDED                                        | Return window over (sweeper)                                                             | `completed_at` + 24 h passed                   | unchanged  | —                                                                                        | stop watching                                                                                    | none                                  |

**Ignored, by design:** a provider status ranked below the current one (`PROCESSING` after `SUCCEEDED`, PAY-11); a repeat of a status already applied; any webhook with a bad signature (it never reaches the machine, PAY-10). Rank: `ACCEPTED`, `PROCESSING` < `SUCCEEDED`, `FAILED` < `RETURNED`.

**Daily limit:** reserved at W0; released at W6, W9 and W13 (no money left); kept at W8, W10 and W11 (money did leave, even if it came back) (ADR-12).

## Deposit

Normal path:

```
CREATED  ->  PENDING  ->  SUCCEEDED
```

| Status    | Meaning                                                                                                                                  | Can move to                                                                         |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| CREATED   | Row exists, PSP payment not created yet. On PSP timeout or 5xx it stays here and a retry resumes (D3)                                    | PENDING (D1), FAILED (D2 PSP 4xx, D5 abandoned after 10 min)                        |
| PENDING   | Payment link issued, waiting for the payer. Stays here while the PSP says INIT or verify is unavailable, and keeps polling (D6, D9, D10) | SUCCEEDED (D8 paid and verified), FAILED (D7 expired, D11 PSP failed, D12 reversed) |
| SUCCEEDED | Final. Wallet credited with the verified amount                                                                                          | none                                                                                |
| FAILED    | Final                                                                                                                                    | none                                                                                |

## Idempotency key

| From        | Event                                      | To                                        | Notes                                                     |
| ----------- | ------------------------------------------ | ----------------------------------------- | --------------------------------------------------------- |
| —           | Single-transaction endpoint claims the key | (inserted, uncommitted)                   | Twins block on the primary key until commit               |
| (inserted)  | Same transaction completes                 | COMPLETED                                 | Response stored; nobody ever sees it `IN_PROGRESS`        |
| —           | Deposit create claims with lease           | IN_PROGRESS (`locked_until = now + 30 s`) | Committed at once                                         |
| IN_PROGRESS | PSP answered (201 or 4xx)                  | COMPLETED                                 | Response stored                                           |
| IN_PROGRESS | PSP ambiguous                              | IN_PROGRESS, lease released               | Retry resumes immediately                                 |
| IN_PROGRESS | Twin arrives, lease valid                  | unchanged                                 | Twin gets 409 `IDEMPOTENCY_IN_PROGRESS`                   |
| IN_PROGRESS | Retry arrives, lease expired               | IN_PROGRESS (new lease)                   | Resumes the same deposit                                  |
| COMPLETED   | Same key, same body                        | unchanged                                 | Stored response replayed with `Idempotent-Replayed: true` |
| COMPLETED   | Same key, different body                   | unchanged                                 | 422 `IDEMPOTENCY_KEY_REUSED`                              |

## Outbox row

| From      | Event                             | To                                                                 |
| --------- | --------------------------------- | ------------------------------------------------------------------ |
| —         | Written in a business transaction | unsent (`published_at` null)                                       |
| unsent    | Relay claims it                   | claimed (`claimed_until = now + 30 s`, `attempts + 1`)             |
| claimed   | Broker confirmed                  | published (`published_at` set)                                     |
| claimed   | Publish failed                    | claimed for a backoff (`30 s × 2^(attempts − 1)`, ≤ 10 min), `last_error` set; unsent again after it |
| claimed   | Relay died, or left it for later  | unsent again when the claim expires                                |
| published | Older than 3 days                 | deleted                                                            |

## Crash at any point: what the restart finds

| Process dies…                                 | Rows show                    | What resumes it                                        | Why nothing is lost or doubled                            |
| --------------------------------------------- | ---------------------------- | ------------------------------------------------------ | --------------------------------------------------------- |
| before the request commits                    | nothing                      | the client retries with the same key                   | nothing happened                                          |
| after commit, before the relay publishes      | PENDING + unsent outbox row  | relay; or the sweeper at `next_check_at` (+30 s)       | requestId already fixed                                   |
| after W1 commit, before the HTTP call         | SUBMITTING, open attempt     | sweeper at +30 s → sync → GET 404 → W5 resubmit        | same requestId; provider de-duplicates                    |
| after the HTTP call, before recording it      | SUBMITTING, open attempt     | sweeper → sync → GET 200 → W7/W8                       | we ask before resubmitting                                |
| after the provider succeeded, before settling | PROCESSING                   | webhook or sweeper → sync → W8                         | `UNIQUE (ref_id) WHERE kind IN (SETTLE, RELEASE)`         |
| after PSP create, before saving the token     | CREATED, key IN_PROGRESS     | client retry after the lease (D4), or abandonment (D5) | the lost token's URL was never shown, so it can't be paid |
| after verify OK, before crediting             | PENDING, PSP says VERIFIED   | sweeper → sync → verify returns 101 → D8               | `UNIQUE (kind, ref)` on journals; `UNIQUE psp_ref_id`     |
| RabbitMQ down for an hour                     | rows waiting, outbox growing | relay and sweeper catch up on restart                  | jobs are ids; state lives in PostgreSQL                   |
